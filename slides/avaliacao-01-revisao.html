Conceitos básicos

Associe cada termo à descrição mais adequada.

TermoDescrição
1. Classe( ) Regra que deve ser sempre verdadeira para um objeto válido
2. Objeto( ) Molde que descreve estado e comportamento de um conceito
3. Invariante( ) Instância concreta, com identidade e estado próprios
4. Encapsulamento( ) Esconder detalhes internos e expor apenas operações que preservam a consistência

✓ Gabarito · Questão 1

Conceitos básicos

TermoRespostaPor quê
1. Classe( 2 ) moldedescreve estado e comportamento; não tem valores próprios
2. Objeto( 3 ) instânciatem identidade e estado próprios, criado a partir da classe
3. Invariante( 1 ) regra sempre verdadeiraex.: saldo nunca negativo, temperatura dentro da faixa
4. Encapsulamento( 4 ) esconde e expõe só o seguroo único caminho para mudar o estado preserva a invariante

🔎 Reforço · Questão 1

Os quatro termos em um só exemplo

class Termostato:                        # CLASSE: o molde
    def __init__(self, temp_inicial):
        self._temp = 21.0
        self.ajustar(temp_inicial)       # já nasce válido

    def ajustar(self, temp):             # ENCAPSULAMENTO: único caminho
        if not 5 <= temp <= 30:          # INVARIANTE: 5 °C <= temp <= 30 °C
            raise ValueError("fora da faixa")
        self._temp = temp

sala = Termostato(22)                    # OBJETO: identidade + estado
quarto = Termostato(18)                  # outro objeto, outro estado

  • ›b) Cite uma consequência prática de manter a regra fora da classe (Versão 1).

✓ Gabarito · Questão 2

Objeto rico × objeto anêmico

a) Quais são quais

Versão 1 = anêmica: só dados; a regra de devolução está fora da classe.
Versão 2 = rica: regra e dados juntos, com estado protegido.

b) Qualquer uma destas vale

  • —a regra pode ser esquecida ou duplicada em outros lugares;
  • —qualquer código pode alterar devolvido direto e violar a regra;
  • —mudar a regra exige procurar usos espalhados.

Basta uma consequência bem justificada para pontuar a letra b.

Questão 4 · 0,25 pt · Bloco 1

Verdadeiro ou falso

Justifique os falsos.

  • ›( ) a) Tornar todos os atributos públicos e criar get/set para cada um garante bom encapsulamento.
  • ›( ) b) Duas instâncias com os mesmos valores de atributo podem ser entidades diferentes, se tiverem identidades diferentes.
  • ›( ) c) Herança é sempre a melhor forma de reaproveitar código.

✓ Gabarito · Questão 4

Verdadeiro ou falso

F a)

get/set para tudo expõe o estado e não protege invariantes. O mesmo vale para atributos públicos.

V b)

Entidade é definida pela identidade, não pelos valores.

F c)

A herança acopla a subclasse à base. Em geral, composição costuma ser preferível.

🔎 Reforço · Questão 4

Getter/setter não é encapsulamento · entidade × valor

Item a · só mudou a sintaxe

class Conta:
    def get_saldo(self): return self._saldo
    def set_saldo(self, v): self._saldo = v

conta.set_saldo(-500)   # aceito! invariante violada

Item a · operação que protege

class Conta:
    def sacar(self, valor):
        if valor > self._saldo:
            raise ValueError("saldo insuficiente")
        self._saldo -= valor

conta.sacar(500)        # a regra mora aqui

Item b · identidade

class Cliente:                              # ENTIDADE: igual se o id for igual
    def __init__(self, id, nome): self.id, self.nome = id, nome
    def __eq__(self, o): return self.id == o.id

Cliente(1, "Ana") == Cliente(2, "Ana")      # False: mesmos valores, identidades diferentes

@dataclass(frozen=True)                     # OBJETO DE VALOR: igual se os valores forem iguais

Coesão e acoplamento

  • ›a) O que é coesão e por que ela deve ser alta.
  • ›b) O que é acoplamento e por que ele deve ser baixo.

✓ Gabarito · Questão 5

Coesão e acoplamento

a) Coesão

Grau em que as responsabilidades de uma classe se relacionam. Alta coesão facilita o entendimento e a mudança.

b) Acoplamento

Grau de dependência entre elementos, em especial dos detalhes uns dos outros. Baixo acoplamento reduz o efeito cascata das mudanças.

Uma definição e a razão. Só a definição vale metade.

✓ Gabarito · Questão 6

Interface e contrato

a) Interface

É um contrato que define quais operações um conjunto de classes deve oferecer, sem dizer como.

b) Depender de abstração

O cliente usa apenas o contrato, sem saber qual implementação concreta recebe. Isso facilita substituição, extensão e testes com dublês.

✓ Gabarito · Questão 9

Reconhecendo o problema

a) Code smell

Cadeia de condicionais por tipo (if-elif/switch) que cresce a cada novo caso.

b) Princípio

OCP (Open/Closed): a cada tipo é preciso modificar a classe existente, com risco de regressão.

c) Padrão

Strategy: uma interface (Tarifa) com custo_por_pagina, uma classe por tipo de tarifa, e Impressao recebe uma estratégia e delega.

d) Novo tipo

Criar uma nova classe que implemente o contrato e passá-la a Impressao, sem tocar nas existentes.

Questão 10 · 0,5 pt · Bloco 3

Strategy em todo lugar?

Um colega propõe aplicar Strategy em um método que só tem uma regra de cálculo, que nunca mudou e para a qual não há previsão de variar.

Você concorda? Explique em duas ou três linhas.

✓ Gabarito · Questão 10

Strategy em todo lugar?

Resposta esperada: não concordo

Sem variação real, o padrão acrescenta complexidade sem benefício (YAGNI). Padrões resolvem problemas: primeiro identifique o problema, e só aplique quando houver variação ou risco de variação plausível.

Dois elementos para pontuar: discordar e justificar com ausência de variação (YAGNI).

🔎 Reforço · Questão 10

Antes do padrão, a pergunta

flowchart TD
  A["Há um ponto de variação<br/>real ou plausível?"] -->|Não| B["Método simples.<br/>Não aplique padrão"]
  A -->|Sim| C["Varia o COMPORTAMENTO<br/>ou a CRIAÇÃO?"]
  C -->|Comportamento| D["Strategy"]
  C -->|Criação| E["Factory"]
  B -.->|surgiu variação depois| A

YAGNI (You Aren't Gonna Need It): não construa flexibilidade para um futuro que ninguém viu chegar. Refatorar para Strategy depois, quando a segunda regra aparecer, é barato.

Questão 11 · 0,5 pt · Bloco 4

Simple Factory

Com relação ao conceito de Simple Factory, estudado em sala de aula:

  • ›a) O que é uma Simple Factory?
  • ›b) Ela é um Design Pattern oficial do catálogo clássico ou uma convenção de organização? Comente.
  • ›c) Qual é o limite dela? (O que ainda acontece dentro dela quando surgem novos tipos?)

✓ Gabarito · Questão 11

Simple Factory

a) O que é

Uma classe/função que centraliza a decisão de qual objeto concreto criar.

b) Padrão oficial?

É uma convenção/idiom, não faz parte do catálogo clássico do GoF.

c) Limite

Continua tendo condicional e centralização: é preciso modificar a factory a cada novo tipo, o que fere parcialmente o OCP.

Simple Factory × Factory Method

a) Quem é quem

A = Simple Factory · B = Factory Method.

b) Quem decide

A superclasse Logistica define o fluxo (planejar_entrega) e deixa criar_transporte como ponto de variação; cada subclasse decide qual concreto instanciar.

c) Outro padrão

A Comanda refatorada

class Comanda:
    def __init__(self, impressora):               # (1) DI
        self._itens = []
        self._fechada = False
        self._impressora = impressora

    @property
    def total(self):                              # derivado dos itens
        return sum(i.preco for i in self._itens)

    def adicionar(self, item):
        if self._fechada:                         # invariante protegida
            raise ValueError("comanda fechada")
        self._itens.append(item)

    def fechar(self, desconto):                   # (2) Strategy
        if self._fechada:
            raise ValueError("já fechada")
        total_final = desconto.aplicar(self.total)
        self._fechada = True
        self._impressora.imprimir(total_final)
        return total_final
class Desconto(ABC):
    @abstractmethod
    def aplicar(self, total): ...

class SemDesconto(Desconto):
    def aplicar(self, total): return total
class DescontoFidelidade(Desconto):
    def aplicar(self, total): return total * 0.90
class DescontoAniversario(Desconto):
    def aplicar(self, total): return total * 0.80

class FabricaPagamento:                           # (3) Simple Factory
    _formas = {"dinheiro": PagamentoDinheiro,
               "cartao": PagamentoCartao}
    @classmethod
    def criar(cls, forma):
        return cls._formas[forma]()
